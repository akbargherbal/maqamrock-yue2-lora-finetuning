# YuE2 generation/merge knobs beyond pron-LoRA `alpha` and checkpoint

Investigation and design only. No training, no GPU generation, no code committed
on this branch beyond this document. Read-only analysis across this repo and a
fresh clone of `0xShug0/audio.cpp`.

**Source pin:** `audio.cpp` @ `ac16661d144f00f84ea0483f3574c374c9868e2d`
(2026-09-24). The `audiocpp_cli` binary used by the sweeps is the sm89-l4 build
(`sha256 97028a71…`); its exact source commit is not recorded in the repo, so
treat the line numbers below as "current upstream behaviour" to re-verify if a
knob is adopted — the option surface has been stable, but see §1's doc-vs-code
flags before trusting either alone.

**Question:** every track so far has been generated by `INFERENCE/run_one.sh`
with a fixed command (`yue2.ar_lora_scale=1.0`, `yue2.nar_lora_scale=1.0`,
`yue2.attention=flash`, `--request-option cot=off`) and only `alpha` and the
pron checkpoint ever varied. What yue2 request / sampling / session options
actually exist in audio.cpp, which are reachable today, what mechanism does each
one touch, and which 2–3 are worth a cheap empirical test against our two
failure modes — pronunciation errors on specific letters (ح خ ع ض) and
recitation-flavor bleed (the failure mode we must avoid, `docs/PRON_LORA.md:7`,
`DECISIONS.md` goal language)?

---

## Recommendation (TL;DR)

Test, in this order, at fixed checkpoint (3050) and fixed `alpha` (0.5), one
knob at a time, on the same Hijaz+Kurd / seed `20260924` setup the fine sweep
already uses:

1. **`guidance_scale` — set it to `1.0`, then `1.5`.** The effective default is
   `1.01` for `cot=off` (`types.cpp:69-74`), so CFG has effectively never been
   used, yet at `1.01` the run already pays the two-stream CFG cost
   (`ar_runtime.cpp:763`). The negative stream is *instruction-only* — no style,
   no lyrics (`pipeline.cpp:53-70`) — so `guidance_scale` is the one knob that
   directly sets how hard the AR follows the lyrics conditioning that carries
   correct pronunciation, and `1.0` vs `1.01` is a clean same-seed A/B against
   the already-rendered `c3050_a0.5`. It cannot cancel the pron adapter (both
   streams share the merged weights), so it is a genuine test of *lyrics
   adherence vs recitation amplification*, not a fix.
2. **`semantic_temperature` — try `0.8`.** The codec-AR temperature has been
   fixed at `1.0`; lowering it is the standard way to make a fine-tuned AR
   commit to its high-probability continuation. Whether that continuation is
   "correct articulation" or "recitation motif" is exactly what a single value
   would tell us; it is one scalar and orthogonal to guidance.
3. **`semantic_repetition_penalty` — try `1.4` (and/or widen
   `semantic_penalty_window` to `100`).** Recitation bleed is plausibly the
   pron adapter's learned repetition/ornament statistics; the default window is
   only 50 frames ≈ 2 s (`ar_runtime.cpp:219-235`), which may be too short to
   penalise longer recitation motifs. This is the most failure-mode-specific of
   the sampling knobs.

Cost of (1)–(3) as designed in §"Proposed minimal test design": **8 tracks
(4 configs × Hijaz/Kurd) ≈ 29 min on the L4**, plus 4 reused reference tracks
that already exist. No training, no new checkpoints, no model re-conversion —
the configs share the same merged rank-40 adapter and differ only in a request
option.

Two things this report does **not** recommend as first tests: NAR-side knobs
(`num_inference_steps`, `yue2.attention`) cannot fix an AR-level property, and
the `abc_*` / `cot` family is dead weight while `cot=off` (the ABC stage is
never run).

## 3. Mechanism + relevance to our two failure modes

The two failures are different subsystems. Pronunciation is an **AR
language-conditioning** property: the AR is the text/next-token path, and the
pron adapter is AR-only (`docs/PRON_LORA.md:4-6`). Recitation bleed is also an
**AR** property — it is what the AR learned on the recitation corpus, measured
in training as `ar_kl = KL(base ‖ lora)` drift (`docs/PRON_LORA_VERIFICATION.md:164-177`).
The NAR only renders the AR's codec stream into audio. This ordering matters:
AR-side knobs can move both failure modes; NAR-side knobs move audio quality but
not the underlying semantics.

**`guidance_scale` (semantic AR).** When `guidance_scale != 1.0`, the pipeline
runs two streams (`ar_runtime.cpp:756-850`): the positive prefix is
`[EOD] + instruction + [Tags] + style + [Lyrics] + lyrics + ABC/MUSIC markers`,
the negative prefix is `[EOD] + instruction + MUSIC_START` — **style and lyrics
are absent** (`pipeline.cpp:31-70`). Logits are combined as
`neg + (pos − neg)·g` (`ar_runtime.cpp:817`). So `g` controls how much of the
logit comes from "the style+lyrics conditioning" versus "the instruction
only". The default `1.01` is essentially no guidance; raising it forces the AR
to lean on the lyrics representation the adapter was trained against, which is
the mechanism most directly tied to pronunciation. The crucial caveat: both
streams run on the **same merged weights**, so `g` cannot subtract the pron
adapter's recitation prior — it can only amplify or dampen how strongly the
conditioning (lyrics) drives sampling. Whether that reduces or worsens bleed is
an empirical question, not a deducible one, which is why it is worth measuring.
Second-order but real: `g=1.0` selects the single-stream `generate()` path
(`ar_runtime.cpp:763`), so the default `1.01` is already paying ~2× AR
prefill/decode for a 0.01 difference in guidance.

**`semantic_temperature` (semantic AR).** Logits are divided by `T`
(`ar_runtime.cpp:304`) before top-k/top-p and softmax. Lowering `T` sharpens the
adapted distribution toward its modes. If the pron adapter's dominant
continuation is the correct phoneme sequence, this helps pronunciation; if its
dominant continuation is a recitation motif, it entrenches bleed. Raising `T`
flattens toward the base distribution, likely diluting both the pron benefit and
the recitation prior. Ambiguous sign, cheap to test, orthogonal to guidance.

**`semantic_top_p` / `semantic_top_k` (semantic AR).** Nucleus / top-k
truncation over the codec logits (`ar_runtime.cpp:238-355`). Mechanically
similar to temperature (mode-seeking) but enforced on the cumulative-mass tail.
The default `top_p=0.95` keeps a wide tail; narrowing to ~0.8 removes unlikely
codec frames, which can suppress both articulation errors and "unusual" musical
transitions. Same ambiguous-sign caveat as temperature.

**`semantic_repetition_penalty` / `semantic_penalty_window` (semantic AR).**
The penalty acts only on the last `penalty_window` emitted frames
(`ar_runtime.cpp:219-235`, `406-417`); the default is 50 frames = 2 s. Recitation
delivery is stereotypically repetitive/ornamented at timescales longer than 2 s,
so the current setting may barely see the patterns we want to suppress. Raising
the penalty and/or widening the window is the most failure-mode-specific
candidate. It is also the riskiest: the same penalty can forbid the legitimate
repetition of a syllable or hook, and can hurt musical structure.

**`num_inference_steps` (NAR).** Midpoint ODE steps; more steps integrate the
flow more accurately. It affects acoustic cleanliness, not the AR's
pronunciation or recitation semantics. **Not connected to either failure mode**
— include only as an audio-quality control, never as the first probe.

**`nar_noise_file` (NAR).** Fixes the NAR noise for reproducibility. Diagnostic
only; **not connected** to either failure mode.

**`yue2.attention` / `yue2.attention_tile_rows` (NAR).** Kernel selection and
tiling; `flash` is already forced and `attention_tile_rows` is a no-op under
flash. Different kernels can change float rounding and flip sampled tokens
(`DECISIONS.md:191`), so it is a reproducibility caveat, not a quality lever.
**Not connected** to either failure mode.

**`yue2.ar_lora_scale` / `yue2.nar_lora_scale`.** These scale the *whole* merged
adapter (style + pron), because audio.cpp has one scalar per file
(`docs/PRON_LORA_MERGE.md:9-16`). Lowering `ar_lora_scale` weakens the v2 style
adapter at the same time as pron, so it is not a clean pron control — `alpha`
already does that decoupling offline. **Entangled; not recommended.**

**`cot` / `abc` / `abc_file` / all `abc_*` sampling.** With `cot=off` the ABC
planner is never invoked (`pipeline.cpp:390-392`), so every `abc_*` knob is inert
today (`guidance_scale` only ever touched the semantic stage anyway — ABC uses
plain `generate()`, `pipeline.cpp:395`). Switching `cot=melody|full` would
introduce a generated ABC plan and require SheetSage2 (`DECISIONS.md:37,55`)
while the LoRA was trained `cot=off` — a change of route, not a sampling probe.
**Not connected under the current regime; do not bundle it.**

**`semantic_min_tokens` / `semantic_max_tokens`.** Length gates only (the EOS is
withheld until `min_tokens`; `max_tokens` is the cap we already vary). A longer
render gives more opportunities for errors but does not change the failure
modes' character. **Not connected** beyond exposure time.

**Seed.** Not a knob for either failure mode, but it is the dominant variance
source and only one seed (`20260924`) has ever been used. Any 2-maqam comparison
is effectively N=2; a within-track A/B or a second seed is needed before
trusting a small difference.

**Weight types / context / arena sizes.** Memory and numerics only. BF16 is
required for correct LoRA merges (`DECISIONS.md:213`). **Not connected.**

  flags are no-ops — use the prefixed `semantic_*`/`abc_*` options." Confirmed
  from source in §1d.
- **The option tables are documented as the source of truth.**
  `DECISIONS.md:224` names `docs/models/yue2.md` as holding the full

  a repo-wide grep for `guidance_scale` / `semantic_temperature` /
  `semantic_top_p` / `semantic_repetition` / `num_inference_steps` returns only
  that one inventory mention.
- **Attention kernel is a VRAM/perf matter, already decided.**
  `DECISIONS.md:170-178`; `PROGRESS.md:305-311`. `flash` is forced; the kernel

- **AR drift is the known pron-adapter risk.** `ar_kl = KL(base ‖ lora)` on AR

  "fewer steps / lower LR / lower `ar_kl_weight`" as the *first* single-variable
  lever. This is the repo's own framing of the bleed risk.
- **Checkpoint `ar_ce`/`ar_kl` are measured.** `PROGRESS.md:692-698`,
  `results/README.md`, `docs/PRON_LORA_VERIFICATION.md:152-162` (table reproduced
  in §5). The repo already notes "sharply diminishing `ar_ce` return after
  3050".
- **Seed reproducibility is an untested hypothesis** (`DECISIONS.md:191`):
  a different GPU/attention kernel can shift floats, flip one sampled token, and
  diverge. Relevant to any knob sample built on a single seed.
- **Every track must carry a sidecar** (`DECISIONS.md:190`), and 3050+final were
  the only checkpoints ever rendered (`results/pron_sweep/README.md`,
  `results/pron_fine_sweep/README.md`).

## 6. Per-layer / selective merge

`merge_pron_lora.py` keeps the LoRA in low-rank form and, for every AR key,
concatenates along the rank dimension: `A = cat([A_style, A_pron])`,
`B = cat([B_style, alpha·B_pron])` (`merge_pron_lora.py:254-266`). The alpha is
folded into the pron B block, per key, inside that loop. `_proj`/`_stem`/`_ab`
(`merge_pron_lora.py:113-134`) recover the projection base name and A/B role, so
the loop already has everything needed to make alpha a **per-key function**.

**Granularity is the catch.** The inputs are *ai-toolkit fused* projections:
`text_encoders.model.layers.{i}.self_attn.qkv_proj`, `self_attn.o_proj`,
`mlp.gate_up_proj`, `mlp.down_proj` (converter `KEY_RE`,
`convert_aitoolkit_yue2_lora.py:39-45`). q/k/v share one A/B pair; gate/up share
one. So a merge-time scale can be varied by:

- **layer index** (0–27), and/or
- **fused module** (attention `qkv_proj`/`o_proj` vs MLP `gate_up_proj`/`down_proj`),

but **not** by unfused projection (q vs k vs v, gate vs up) — those are produced
later by row-slicing B in the converter (`convert_aitoolkit_yue2_lora.py:70-79`),
and one alpha per fused tensor scales them together.

**Verdict: "a few lines of code", not a redesign.** Concretely: add an alpha
resolver keyed on `(layer, module)` in `merge()`, replace the two `alpha`
references (`merge_pron_lora.py:262`) with it, add CLI args
(e.g. `--alpha-attn`, `--alpha-mlp`, `--alpha-layers 14-27`), and record the map
in metadata. No change to the converter is needed. One constraint: to keep the
converter's single uniform rank (`convert_aitoolkit_yue2_lora.py:207-208`), every
key must still receive the pron block at rank 40 — groups you want to disable
get a **zero** block (`alpha=0`) rather than omission, exactly as the current
alpha=0 path drops only when alpha is globally 0 (`merge_pron_lora.py:237-266`).

**But there is no evidence to pick the split.** Nothing in the repo says whether
recitation delivery lives in attention vs MLP, or in early vs late layers.
Blindly splitting is guesswork. A cheap, evidence-producing first step is to
extend `offline_ar_loss_replay.py` to ablate fused-module groups (merge with a
zeroed group, replay the 180 val pairs) and see which group carries `ar_ce`
(pronunciation) vs `ar_kl` (drift). Only then is selective merging worth it.

## 7. `semantic_prefix`

**How it works.** `semantic_prefix` / `semantic_prefix_file` parse a flat JSON
array of codec indices, each in `[0, 32768)`, one per 25 fps frame
(`request.cpp:58-111`). They become **forced history**: the AR prefills them
behind the prompt and samples from frame N onward (`docs/models/yue2.md:246-286`;
`pipeline.cpp:179-199`). The returned stream — and therefore the NAR stage and
the audio — includes the forced frames. `semantic_max_tokens` must be ≥ N
(enforced at `request.cpp:198-199`; also `semantic_min_tokens` and the penalty
window count the forced frames, `yue2.md:254-257`). If N ≥ `semantic_max_tokens`,
the AR stage is skipped entirely and the forced frames are returned as-is
(`pipeline.cpp:180-189`).

**CFG interaction.** With `guidance_scale != 1.0` the forced frames are appended
to **both** the positive and negative prefixes (`ar_runtime.cpp:774-782`) and
that path prefills through host K/V, so memory grows with N and the run is
double-streamed (`yue2.md:296-299`). With the yue2 effective default `1.01` for
`cot=off`, a prefix therefore takes the expensive path; setting `guidance_scale=1.0`
switches to the single-stream device-prefill path.

**Can a baseline (alpha=0) token stream anchor a pron-merged generation?** Yes,
mechanically: export semantic tokens from an `a0` run, then feed them as
`semantic_prefix_file` to a pron-merged run. The first N frames are then literally
the v2 baseline's rendition, and because they become conditioning history they
pull the continuation toward that (rock, non-recitation) delivery. This is a
plausible way to anchor the opening away from recitation.

**What export requires:** the `a0` run needs `export_semantic=true` **and**
`--out-dir` (the CLI only writes `semantic.json` when `--out-dir` is set;
`docs/models/yue2.md:175-198`), or equivalently `stop_after=semantic` (which
implies `export_semantic=true`, `request.cpp:184-187`). `run_one.sh` currently
passes neither, so this needs a wrapper/`--out-dir` addition. A prefix run needs
`semantic_prefix_file=<json>` with `semantic_max_tokens ≥ N`; with
`cot=off` no ABC is required (`request.cpp:201-203`).

**Honest limits.** (a) The prefix does not reproduce the uninterrupted run's
draws — the sampler RNG starts at frame N and prefilled K/V differ numerically
from step-decoded K/V (`yue2.md:292-294`). (b) It anchors *content*, not the
continuation's *style*: the pron adapter still drives sampling after frame N, so
drift can resume a few seconds in. (c) With `guidance_scale≠1.0` the prefix path
is the memory-heavy host-K/V path. This is worth a small probe, but it is an
anchor, not a cure.

## Honest tradeoffs

- **Sampling knobs reweight; they do not remove the adapter.** Temperature,
  top-p/top-k, and repetition penalty all act on the *adapted* AR distribution.
  If pronunciation and recitation both live in that distribution, no sampling
  setting decouples them — at best it changes which one dominates. The report
  claims no direction, only that the sign is measurable in ~an hour.
- **Guidance cannot cancel the pron adapter.** The negative stream omits style
  and lyrics, not the adapter (both streams use the merged weights). So a high
  guidance may amplify lyrics adherence (good for pronunciation) *or* amplify a
  lyrics-triggered recitation prior (bad for bleed). This is the single most
  mechanistically relevant untested knob and also the one whose sign is least
  predictable.
- **Statistical power is the binding constraint.** Two maqams, one seed, one
  listener, 1–5 ratings. A 1-track difference is not signal. The design below
  reuses the seed and prompts so each knob is a same-seed A/B against an existing
  reference; still, treat any result as a hypothesis, not a verdict.
- **Selective/per-layer merge is cheap mechanically but evidence-free.** The
  code change is small (§6); choosing which projection to scale is the hard part,
  and a wrong split could simultaneously lose pronunciation and keep bleed. An
  ablation replay should precede it.
- **`semantic_prefix` is an anchor, not a fix.** It can lock the opening to the
  baseline's delivery, but drift can resume; the CFG-path memory cost and the
  non-reproducible RNG make it a more involved experiment than a scalar knob.
- **Everything here is secondary to the checkpoint question.** The repo's own
  analyses name AR drift as the risk (`ar_kl`), and 1525/4575 have never been
  rendered. A sampling sweep at 3050 is complementary; it is not a substitute
  for auditioning the low-drift checkpoint.

## Proposed minimal test design (design only — do not run)

**Anchor (held fixed across every new track):** pron checkpoint **3050**,
`alpha = 0.5`, maqams **Hijaz + Kurd**, generation seed **20260924**, auto cap
(7250 / 6500), same staged prompts and sm89 binary as the fine sweep, strictly
sequential (two concurrent runs can OOM the NAR graph, `docs/PRON_LORA_SWEEP.md:27-29`).
`c3050_a0.5` and `a0` already exist at this seed/maqam and are **reused as
references, not regenerated** (`results/pron_fine_sweep/README.md:5-8`), so
`c3050_a0.5` (guidance `1.01`) is the direct comparator for K1.

**Configs (one knob changed from `c3050_a0.5`; 4 × 2 maqams = 8 tracks):**

| id | request option(s) | why this value |
|---|---|---|
| `c3050_a0.5_g1.0` | `guidance_scale=1.0` | same-seed A/B vs the reused `c3050_a0.5` (1.01); isolates the lone guidance value *and* the single- vs two-stream code path |
| `c3050_a0.5_g1.5` | `guidance_scale=1.5` | first real guidance step; tests whether lyrics adherence changes pronunciation/bleed |
| `c3050_a0.5_t0.8` | `semantic_temperature=0.8` | mode-seeking; sharpens the adapted AR |
| `c3050_a0.5_rp1.4` | `semantic_repetition_penalty=1.4` | targets repetition/ornament patterns; window left at 50 |

Optional fifth if the first four are informative: `c3050_a0.5_p0.8`
(`semantic_top_p=0.8`) → 10 tracks total. Add a `c3050_a0.5_t1.2` only as a
follow-up if `t0.8` moves in a bad direction.

**Cost:** ~218.5 s/track mean measured in the fine sweep → **8 tracks ≈ 29 min**
on the L4, 10 tracks ≈ 36 min. No merge/conversion changes: all five
`c3050_a0.5_*` configs share the same rank-40 AR/NAR adapters; only the CLI
command differs, so the reused `c3050_a0.5` files are directly comparable.

**Tooling needed (proposed, not applied):** `run_one.sh` has no way to pass
extra request options. The smallest change is an `EXTRA_REQUEST_OPTS` env that
expands into repeated `--request-option` flags:

```diff
--- a/INFERENCE/run_one.sh
+++ b/INFERENCE/run_one.sh
@@
 status="$OUT/_runs_status.log"
+
+# Extra request options, space-separated key=value pairs (e.g.
+# EXTRA_REQUEST_OPTS="guidance_scale=1.5 semantic_temperature=0.8").
+extra_request=()
+for kv in ${EXTRA_REQUEST_OPTS:-}; do
+  extra_request+=(--request-option "$kv")
+done
@@
   --request-option style="$(cat "$style")" \
   --request-option cot=off \
   --request-option semantic_max_tokens="$CAP" \
+  "${extra_request[@]}" \
   --seed "$S" \
```

A `INFERENCE/pron_knob_probe.sh` driver then mirrors `pron_fine_sweep.sh`:
one folder per config, `EXTRA_REQUEST_OPTS` per config, resumable on
WAV + `Exit status: 0`, failures to `_failed.log`, and a manifest recording the
config, exact option values, adapter sha256, prompts, seed, cap, and binary
sha256 (`DECISIONS.md:190` sidecar policy). Blinding: a new seed as in the fine
sweep, labels only.

**Phase 2 (checkpoint, evidence-grounded):** merge and render
`c1525_a0.5` and `c4575_a0.5` on the same Hijaz+Kurd/seed setup (4 tracks, ~15
min). This directly tests the drift hypothesis from §5 — 1525 has `ar_kl` 0.72
vs 3050's 1.27 — and needs no `run_one.sh` change (only `LORA_AR`/`LORA_NAR`,
already supported).

**Verdict protocol:** reuse `PRON_FINE_SWEEP_INPUT/`'s blinded 1–5 rating +
recitation-bleed flag, per maqam, and compare each knob track against the reused
`c3050_a0.5` reference. Decide "does this knob move the needle at all" before
deciding a best value; do not pick a winner from 2 tracks.
